# StudySeq / 知序 V1.2 PRD

## 文档定位

本文件是 StudySeq / 知序 V1.2 版本的产品需求文档（PRD）。

- V1.2 是存量桌面应用的增量小版本，不是新产品，也不是平台扩张。
- 本文件只做产品层判断：哪些候选功能进 V1.2、哪些继续后置、各自的验收标准。
- 技术实现方案不在本文件展开，留给后续技术设计文档。
- 本文件文风与 `product/docs` 下现有文档保持一致：务实、克制、轻量。
- 本版本范围已经用户评审定稿（2026-06-12）。

## 版本目标

> V1.2 主题：让长资料更好导航，让资料区像真正的资源管理器，支持视频这一新资料形态。

V1.2 在 V1.1（继续阅读与资料治理）的基础上，补齐三块体验：长 PDF 的目录导航、资料区的文件夹组织与大图标平铺浏览、基础格式的视频播放。它不引入新解码内核或转换引擎——视频播放依托 WebView 原生解码能力，只支持其原生支持的格式。

V1.2 不追求功能数量，宁可少而精。一个个人开发者维护的桌面小版本，能稳定交付 3 项真正补齐体验的能力，比塞满 6 项半成品更有价值。

## 候选功能与优先级判断

V1.1 阶段，以下 6 项被明确排除在外，作为 V1.2 候选。经用户评审，定稿如下。

### 进入 V1.2

| 优先级 | 功能 | 一句话理由 |
| --- | --- | --- |
| Must | PDF 目录（大纲） | pdfjs 原生提供大纲数据，零新依赖，直接接入详情页内嵌阅读主线，显著提升长 PDF 的可用性。 |
| Must | 视频资料播放（基础格式） | WebView2 为 Chromium 内核，MP4（H.264/AAC）与 WebM 可由 HTML5 video 原生解码，无需自带播放内核；先落地好做的格式。 |
| Should | 资料文件夹（资源管理器式资料区） | 把资料区升级为"大图标、文件夹/文件平铺"的资源管理器样式，并支持文件夹归类；是产品既定设计的完整落地，但 UI 与数据改动面最大，列为 Should。 |

### 不做 / 继续后置

| 功能 | 结论 | 理由 |
| --- | --- | --- |
| 阅读页滚动位置保存 | 不做（用户评审裁定） | 详情页内嵌阅读为翻页式且阅读区较小，V1.1 已按资料恢复页码与缩放，滚动位置的增量价值有限。 |
| PDF 全文搜索 | 不做（用户评审裁定） | 需逐页提取文本建检索，成本明显高于目录、价值密度更低。 |
| Office 资料预览 | 本版本不做 | Tauri 下无原生 Office 渲染能力，需转换引擎或重型库，可行性与包体积风险大，与轻量小版本定位冲突。 |
| 笔记分组 | 继续后置 | 当前笔记规模下价值不紧迫；避免同一版本同时改资料和笔记两套组织结构，待资料文件夹落地后再观察决定。 |

判断口径说明：

- PDF 目录直接落在现有 pdfjs 阅读主线上，是最低风险、最高确定性的增量，列为 Must。
- 视频播放依托 WebView 原生解码，范围严格限定在原生支持的格式（MP4/WebM），不引入任何解码依赖，列为 Must；超出原生能力的格式（MKV、AVI、FLV 等）明确不支持并给出友好提示。
- 资料文件夹是产品既定方向（V1 设计即为"资源管理器式大图标布局"，V1 实现简化为列表），但属详情页结构性改动且需要数据库迁移，单独列为 Should，在两项 Must 稳定后再推进。

## 入选功能详细需求

### 功能一（Must）：PDF 目录（大纲）

#### 用户故事

作为一名阅读长篇 PDF 的用户，我希望能看到这份 PDF 的目录结构，并点击目录直接跳转到对应章节，而不是靠翻页一页页找。

#### 功能描述

- 在详情页内嵌 PDF 阅读区，提供该 PDF 的目录（大纲）入口。
- 目录数据来自 PDF 自身的大纲信息，由现有 pdfjs 能力读取，不引入新依赖。
- 目录支持点击跳转到对应位置；跳转与现有页码恢复、缩放逻辑兼容。
- 目录入口在不需要时可收起，不挤占主阅读区，符合留白、轻层次的视觉语言。

#### 验收标准

1. 打开一份带大纲的 PDF，能看到与该 PDF 实际大纲一致的目录条目。
2. 点击目录条目，能跳转到对应页 / 位置。
3. 打开一份不带大纲的 PDF，目录区给出"该 PDF 无目录"之类的明确空状态，不报错、不显示空白控件误导用户。
4. 目录跳转后，现有页码显示、缩放比例的保存与恢复逻辑仍正常工作。
5. 目录入口可展开和收起，收起后不影响主阅读区布局。
6. 多级目录（章 / 节）能体现层级，不把层级压平成一行。
7. 断网状态下，上述流程全部可用。

#### 范围外

- 不做 PDF 全文搜索（用户评审裁定不做）。
- 不做用户自定义目录 / 书签（PDF 自带大纲之外的人工标注不在本版本）。
- 不做目录搜索过滤；本版本只做目录的展示与跳转。

### 功能二（Must）：视频资料播放（基础格式）

#### 用户故事

作为一名用视频学习的用户，我希望把课程视频导入资料库后能直接在 App 内播放，而不是必须切换到外部播放器。

#### 功能描述

- 支持把视频文件作为资料导入（沿用现有导入模式：复制到 App 管理的本地资料库）。
- 在详情页内嵌阅读区播放视频，能力依托 WebView 原生 HTML5 video 解码，不引入自带播放内核。
- 第一批支持格式：**MP4（H.264 + AAC）、WebM（VP8/VP9）**。
- 不支持的视频格式（MKV、AVI、FLV、RMVB 等）在点击时给出明确友好的"暂不支持该格式"提示，不报错、不白屏。
- 播放控件采用原生 video 控件能力：播放 / 暂停、进度拖动、音量、全屏。
- 大文件以流式方式加载（具体机制留给技术设计；现有 PDF 的 data URL 方案不适用于视频）。

#### 验收标准

1. 能导入 MP4、WebM 视频为资料，导入行为（复制到 App 库、同名追加后缀）与现有资料一致。
2. 点击 MP4 / WebM 资料，能在详情页内嵌区域播放，支持播放 / 暂停、进度拖动、音量调节、全屏。
3. 数百 MB 级的视频文件能正常打开并拖动进度，不出现整文件读入内存导致的卡死。
4. 点击不支持的视频格式，给出明确的"暂不支持该格式"提示，App 不崩溃、不白屏。
5. 视频资料的重命名、删除（含二次确认、只删 App 副本）与现有资料行为一致。
6. 删除学习内容时，视频资料随级联删除一并清理。
7. 资料库统计正确计入视频文件的空间占用。
8. 断网状态下，上述流程全部可用。

#### 范围外

- 不支持 WebView 原生解码能力之外的格式（不自带解码器；MKV 等格式后置）。
- 不做播放进度记忆（类比阅读状态的"继续播放"留待后续版本评估）。
- 不做倍速播放、字幕加载、截图笔记等增强能力（后续按需求评估）。
- 不做视频转码。

### 功能三（Should）：资料文件夹（资源管理器式资料区）

#### 用户故事

作为一名资料逐渐变多的用户，我希望资料区像系统资源管理器一样：大图标、文件夹和文件平铺展示，能把资料按文件夹归类、进入文件夹浏览，而不是所有文件都平铺在根目录的列表里。

#### 功能描述

- 把详情页资料区从现有列表样式升级为"资源管理器式"布局：**文件夹块与文件块以大图标平铺，图标下方显示名称**（V1 设计的完整落地）。
- 支持在资料区新建文件夹，并把资料放入文件夹。
- 支持进入文件夹、返回上级（面包屑或返回操作），形成可浏览的层级。
- V1 技术设计已预留 `material_items.parent_id` 字段与 `list_material_items(learning_content_id, parent_id)` 接口形态；当前实现库表尚未落地该字段，需要一次数据库迁移。
- 导入资料、重命名、删除等现有资料能力需在文件夹层级下保持一致行为。
- 点击文件块仍进入现有内嵌阅读（txt / 图片 / PDF / 视频）。
- 删除文件夹时必须二次确认，并明确提示其内部资料的处理方式。

#### 验收标准

1. 资料区以大图标平铺展示文件夹与文件，图标下显示名称，视觉风格符合蓝天极简语言。
2. 能在详情页新建文件夹；能把资料放入文件夹；进入文件夹后能看到其中的资料。
3. 能从文件夹返回上一级；当前所处层级对用户清晰可见（如面包屑或路径提示）。
4. 在文件夹内导入资料时，资料归属于当前文件夹；同名资料导入仍自动追加后缀。
5. 文件夹内资料可重命名、可删除、可点击进入内嵌阅读，行为与根目录一致。
6. 删除文件夹前二次确认，并明确提示内部资料如何处理（随删 / 需先清空，由实现确定其一并在文案中讲清）；删除只作用于 App 管理副本，不删除用户原始来源文件。
7. 删除学习内容时，其下所有文件夹和资料随级联删除逻辑一并清理，不残留孤儿记录或孤儿副本。
8. 旧版本数据库升级后，既有资料完整保留在根目录，文件夹能力可用。
9. 文件夹层级、文件归属在关闭重开 App 后保持一致。
10. 资料库统计在引入文件夹后仍统计正确，不漏算文件夹内资料。
11. 断网状态下，上述流程全部可用。

#### 范围外

- 不做拖拽移动资料 / 文件夹（移动可用菜单或操作入口实现，拖拽交互留待后续）。
- 不做跨学习内容的资料移动。
- 不限制文件夹嵌套层数到固定值，但本版本不为深层嵌套做额外优化体验。
- 不在本版本引入笔记分组（笔记组织结构维持现状）。

## 建议实现顺序

1. **PDF 目录（大纲）（Must）**
   理由：接在现有内嵌 PDF 阅读主线上，依赖现有 pdfjs 能力，无新依赖、无数据库迁移，是最低风险的增量，先拿确定性收益。

2. **视频资料播放（Must）**
   理由：纯增量能力（新增一种可预览的资料类型），不改动既有资料逻辑结构；主要工作在流式加载机制与格式检测，风险中等，独立性强。

3. **资料文件夹（Should）**
   理由：属详情页结构性改动，需要数据库迁移，且触及导入、重命名、删除、级联删除和资料库统计多处既有逻辑，回归面最大，放在两项 Must 稳定之后再做。

排序原则：先做无迁移、低风险、彼此独立的增量，最后做改动详情页结构与数据模型、影响面最大的资料文件夹。

## 风险与开放问题

本节只点到为止，技术细节留给后续技术设计文档。

### 视频大文件的加载机制

现有 PDF 预览采用 data URL 方案，对数百 MB 的视频不可行。需要在技术设计中确定流式加载路径（如 Tauri asset 协议的范围请求能力），保证进度拖动可用且内存占用可控。这是视频功能最主要的技术风险。

### 视频格式与编码的边界判定

同为 `.mp4` 后缀的文件可能使用 WebView 不支持的编码（如 H.265）。需要明确"不支持"的判定与提示策略：按后缀预判、按实际解码失败兜底，或两者结合；保证用户得到的是明确提示而不是黑屏。

### PDF 大纲数据的可靠性

并非所有 PDF 都带大纲，部分 PDF 大纲层级或目标页信息可能不规范。需要明确无大纲和大纲异常时的空状态与降级表现，避免误导用户。

### 资料文件夹对既有逻辑的回归风险

引入文件夹会改动导入、重命名、删除、删除学习内容级联清理和资料库统计等多处既有逻辑，并需要一次数据库迁移（落地 `parent_id`）。删除文件夹时内部资料的处理策略需在实现前定清楚（随删还是需先清空），并保证"只删 App 管理副本、不删用户原始来源文件"的既有安全口径不被破坏。旧库升级路径必须保证既有资料无损。

### 后置项的明确边界（开放问题留给后续版本）

- **PDF 全文搜索**：用户评审裁定不做；后续是否重启，待目录上线后按真实使用反馈决定。
- **Office 预览**：在 Tauri 下走"转 PDF 后 App 内阅读"还是其他路径，技术可行性需单独验证后再立项，本版本不承诺。
- **视频格式扩展**：MKV 等需自带解码器的格式，待基础格式落地、确认真实需求后再评估成本。
- **视频播放进度记忆**："继续播放"与现有"继续阅读"体验同构，待视频基础能力落地后评估。
- **笔记分组**：建议在资料文件夹落地、观察用户实际组织习惯后，再决定笔记是否需要同样的分组能力，避免过早引入不必要的层级。

## 版本边界小结

V1.2 做：

- PDF 目录（大纲）。
- 视频资料播放（MP4 / WebM，依托 WebView 原生解码）。
- 资料文件夹（资源管理器式大图标资料区）。

V1.2 不做（用户评审裁定或继续后置）：

- 阅读页滚动位置保存。
- PDF 全文搜索。
- Office 资料预览。
- 需自带解码器的视频格式（MKV、AVI、FLV 等）。
- 笔记分组。
- 任何引入云同步、账号、新解码 / 转换内核或日历中心布局的能力。

V1.2 守住的硬约束：

- 技术栈不变：Tauri 2 + Vite + React + TypeScript + Rust + SQLite，本地优先、离线优先、无云同步。
- 视觉语言不变：蓝天灵感极简风，留白、轻层次、少边框，不采用日历中心布局。
- 阅读能力只接入详情页内嵌阅读主线，不复活旧独立阅读页。
- 前端只通过 Tauri invoke 调 Rust command；SQLite 只由 Rust repository 访问。
